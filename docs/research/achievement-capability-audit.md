## Existing state, attribution and recovery mechanisms

`LegacyAchievementsReforgedCharDB` is a **per-character** SavedVariables table (`TOC:9`). `LegacyAchievementsReforgedDB` holds account settings and character snapshots (`TOC:8`, `Core:1799–1808`). A SavedVariables table preserves addon observations across reloads, but it cannot recover actions that happened before installation or while the observing addon was disabled.

`Core:15–33` defines `done` timestamps, `money`, named critters/pests/books, distinct consumed food/drink IDs, maximum observed skill ranks, fishing zones and rare fish, boss/rare kill observations, maximum observed reputations, owned items and one-off flags. Extra fields include `dailyDays`, `explorationEvidence`, `characterCollectionEvidence`, `featOwnershipEvidence`, `trackingIdentity`, `completionAttribution` and `moneyTracking`. These fields have different provenance; a boolean or positive integer is not automatically an authoritative historical record.

Current attribution safeguards include `Proof.CharacterIdentity` / `CharacterScope` / `BindCharacter` (`Core:124–198`), completion attribution (`Core:203–228`), and character-bound collection/exploration/ownership evidence. Identity uses realm plus a readable player GUID, or an exact full Forever name fallback; incomplete identity leaves progress unavailable. `BindCharacter` expressly does not attribute old `done` history to new observations. However, `CompletionStatus` retains ordinary non-exploration per-character completion compatibility from a valid old timestamp (`Core:667–678`); do not describe every existing legacy award as newly verified exact-criteria evidence. Code fields named `verified` mean the addon's internal evidence contract; they do **not** mean a tracking family passed this research brief's controlled client-verification requirement.

Login runs quiet `CheckAll` twice after three seconds for history/metas (`Core:2040–2066`). This evaluates existing progress functions. It is not a new authoritative source and cannot convert any source's missing history into recoverable credit. Only records whose exact requirements are already true in queryable state can be recovered. `Available` filters unsupported/class/faction/dependency records (`Core:1812–1819`). Account snapshots are elsewhere indicators, not a substitute for this character's completion (`Core:1822–1826`).

## Capability families

### 1. Completed quests, quest chains and class quests

**Interfaces used:** `C_QuestLog.GetAllCompletedQuestIDs()` returns an ID array; fallback `GetQuestsCompleted(outTable)` fills keys, which the code converts to an array (`Core:454–464`). `C_QuestLog.IsQuestFlaggedCompleted(questID)` / `IsQuestFlaggedCompleted(questID)` returns completion state (`Core:474–477`). Native statistic **98** is authored “Quests completed” (`Extra:469–473`); `QuestCount` prefers a positive parsed statistic over the number of distinct completed IDs (`Core:466–471`). `QUEST_TURNED_IN` refreshes later (`Core:2070–2072`).

**Units and scope:** Exact ID flags can support “complete these specific quests,” provided they are persistent **character** flags. The number of flag IDs can include hidden/autocomplete flags and is not necessarily number of turn-ins. A repeatable quest can be completed repeatedly while retaining only one flag; repeated turn-ins cannot be reconstructed from unique flags. Statistic 98 could measure different things; verify instead of equating the two. Faction conversion, alternative chain branches, server custom IDs and hidden prerequisite flags must be tested individually.

**Existing mapper:** Loremaster uses external `_G.QuestDB.Exists(id)` and `.Get(id,"zoneOrSort")` to count completed IDs against generated continent area lists (`Core:503–524`, `DataQuests:116–119`). The legacy lists include content from another era and cannot define a new Forever checklist without auditing IDs/reachability. Green Hills uses IDs **338,208** (`DataQuests:120`, `Core:841–843`); broad Loremaster, quest totals, Dreadsteed and Charger already exist.

**Fair candidate path:** Explicit curated stable IDs/allowed alternatives can be backfillable and fair to existing level-60 characters. Until the **actual** list is defined and tested, vague “eligible zone checklist” or “major class quest” is HOLD — UNVERIFIED, not a verified addition. A class quest with purchasable alternative mount/spell completion must use the actual quest flags if the criterion says “complete the quest.”

**Pending test Q:** On one eligible character with a known completed chain, capture exact completion flags and completed-ID presence before turning in anything. Test a new chain step, a canceled/abandoned quest, a repeatable quest twice and a hidden flag. Relog; run with production addon disabled then re-enable. Compare another character and the other faction/class where appropriate. Record build, each ID, boolean/nil/error, prerequisite/alternative reachability and whether data becomes ready only after a query/UI event. No claim of all-history recovery follows from one flag.

### 2. Reputation and supply factions

**Interfaces used:** `C_Reputation.GetFactionDataByID(factionID)` reads `.currentStanding`; legacy `GetFactionInfoByID(factionID)` uses its **sixth** return (`Core:1343–1353`). Existing code assumes absolute classic standing **42000 = Exalted**, **9000 = Honored**, remembers maximum observed standing and produces one Exalted achievement for each authored Forever faction (`Core:1357–1365`, `:1413–1419`, `:1453–1458`). Missing APIs/data fall back to zero; that is an existing source behavior, not reliable negative proof for new candidates.

**Correct authored identities:** **2586** = Azeroth Commerce Authority; **2587** = Durotar Supply and Logistics (`Extra:175–176`). **2787** is authored **Earthen Ring**, not a supply faction (`Extra:186`). Identity remains a build-70338 test obligation; do not substitute guessed IDs. `rep2586` and `rep2587` already cover **Exalted**, so new Exalted versions are duplicates of existing source records. Do not assume the factions actually reach that rank/cap in Forever because the source generates those records.

**Semantics:** Current standing supports an explicitly current-state requirement. It does not establish lifetime turn-ins, delivered supplies, highest rank ever, unchanged-faction history or exact currency spent. Addon `reps` maxima recover only ranks previously observed by this addon. Native milestones could prove their own exact reputation criteria after attribution tests. Account/character scope, standing-scale fields, rank/cap, friendship/paragon/special reputation and supply turn-in mechanics remain unverified.

**Pending test R:** Query both IDs once on eligible Horde/Alliance characters, capture identity/name/rank/standing/bounds/warband-account fields as actually returned. Compare reputation panel. Perform **one** supply turn-in, capture before/after and whether an unrelated currency changes. Relog and query with addon disabled/re-enabled. If safe existing samples at a higher/lower rank are available, compare them; do not require destructive reputation loss. Test cap/rank from client records or known capped character. A current-state Honored/Revered design can then be considered, but threshold variants should be clearly labeled rather than counted as distinct new objectives.

## Existing assumptions not to inherit for new achievements

Research phase makes **no production edits** to these behaviors. Preserve existing progress and compatibility while clearly recording that the following are not valid proof for new exact lifetime criteria:

- Fishing skill-minus-one floor and maximum of unlike statistics/catch windows (`Core:1057–1062`, `:2353–2363`).
- Account-wide Quick Fish sums used without per-character historical attribution (`Core:1088–1137`).
- Maximum observed reputation/skill assumed to mean full preinstallation historical maximum (`Core:1006–1032`, `:1357–1362`).
- Generic statistic non-digit stripping and universal displayed “Character” scope (`Core:446–449`, `Statistics:134–135`).
